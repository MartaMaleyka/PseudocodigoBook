Chapter 1

You're not dumb, you just started at the end

I'm going to tell you something that almost made me quit programming.

My first language was Python. One day I spent three hours trying to figure out why my program wasn't working. The culprit? A : I had forgotten. Another day it was an = where there should have been an ==. Three hours over two dots.

Meanwhile, everyone around me seemed to get it, and I didn't. I was one click away from giving up on everything.

What saved me wasn't studying more syntax. It was realizing this: I was writing code without knowing what I wanted it to do. The problem wasn't my talent. I was starting at the end.

Think first, then write. Mistakes aren't your enemy, they're your clue.

Two ways to start

🔥 Code first

  1. I open the editor.
  2. I write whatever comes to mind.
  3. It fails.
  4. I change things at random.
  5. It fails differently.
  6. I get frustrated and think I'm not cut out for this.

🌱 Plan first

  1. I say what I want in one sentence.
  2. I write the steps in plain language.
  3. I test them with pencil and paper.
  4. Only then do I write code.

A very simple example: do I take an umbrella?

Before thinking about languages, think about steps. Here is the plan, written in plain English the way a person would say it:

START
  READ rain       // "yes" or "no"
  READ clouds     // "many" or "few"
  IF rain = "yes" THEN
    WRITE "Take an umbrella"
  ELSE
    IF clouds = "many" THEN
      WRITE "Better take it, just in case"
    ELSE
      WRITE "Head out, no worries"
    END IF
  END IF
END

Now let's test it by hand: the desk check

A desk check means acting as the computer with pencil and paper: you pick example values, follow the plan line by line, and write down what happens. No installation needed.

We'll try three cases. Notice the "deciding line" column: it tells you which path the plan took.

When it's time to write real code, you'll already know what you want to do, and the syntax becomes a translation detail, not a three-hour nightmare.

🚦 Extra practical case: the traffic light

A good desk check doesn't just confirm what works. It also uncovers what you forgot. Look at this first attempt:

START
  READ color
  IF color = "red" THEN
    WRITE "Stop"
  ELSE
    IF color = "yellow" THEN
      WRITE "Get ready"
    ELSE
      WRITE "Go"
    END IF
  END IF

Case D is a color that doesn't exist on a traffic light, and the plan says "Go"! A plan without that test would have sent someone across the street on an invented color. The fix is to ask explicitly about green and leave the last ELSE for unexpected data:

START
  READ color
  IF color = "red" THEN
    WRITE "Stop"
  ELSE
    IF color = "yellow" THEN
      WRITE "Get ready"
    ELSE
      IF color = "green" THEN
        WRITE "Go"
      ELSE
        WRITE "Invalid color"
      END IF
    END IF
  END IF
END

With this plan, case D now outputs "Invalid color". Moral: always ask yourself, "what if they type something I didn't expect?"

Chapter 2

The trick: the language matters least

The question I hear most is: "Which language should I start with? Python? Java? JavaScript?" And people freeze. Whole months go by reading comparisons without writing a single line.

Here's what I wish someone had told me: that's not the important question.

The recipe for a stew

Think of a hearty stew. The recipe (what goes in first, how long it simmers, when the vegetables go in) is the same in your kitchen or your grandmother's. What changes is the pot, the stove and the fire.

Programming works the same way: languages are the kitchen; pseudocode is the recipe. If you master the recipe, you can cook in any kitchen.

The translation map

All languages do the same basic things. They just change the names:

READAsk for dataAsk the user for something.
←StorePut a value into a named "box".
IF … ELSEDecideTake one path or another depending on a condition.
WHILERepeatDo something over and over until something becomes true.
WRITEShowDisplay a result on screen.

Each language has its own way of saying these five things. In chapter 8 we'll look at them side by side. For now, keep the idea: if your plan is solid, translating it is just a matter of practice.

A real example: the invoice with ITBMS

ITBMS is the 7% tax added to a purchase in Panama. Notice that this plan doesn't mention any language and works for all of them:

START
  READ subtotal
  itbms ← subtotal * 0.07
  total ← subtotal + itbms
  WRITE "ITBMS: ", itbms
  WRITE "Total to pay: ", total
END

Chapter 3

What is pseudocode? It's writing in plain language what you want to happen

"Pseudo" means "almost". Pseudocode is almost code: you understand it, a computer doesn't. And that's an advantage, because there's no semicolon you can forget.

There are no official rules, but I recommend these six "house rules" so you don't get tangled up:

START … END1. Everything has a beginning and an endThat way you know where your plan starts and where it finishes.
READ · WRITE2. In and outREAD asks for a value; WRITE shows a result.
←3. The arrow stores, the equals sign asksx ← 5 stores a 5 in x. x = 5 asks whether x is 5.
IF … ELSE … END IF4. Every IF gets closedIf you open a decision, close it with END IF.
WHILE … END WHILE5. Repetition gets closed tooWe'll look at it in depth in chapter 4.
indentation6. What's inside is indented to the rightAnd use clear names: price, not p.

Example: did I pass or not?

At a school in Panama, grades go from 1 to 5, and you pass with 3 or higher. You have three grades and want to know whether you passed:

START
  READ grade1
  READ grade2
  READ grade3
  sum ← grade1 + grade2 + grade3
  average ← sum / 3
  IF average ≥ 3 THEN
    WRITE "Passed with ", average
  ELSE
    WRITE "Time to review. Average: ", average
  END IF
END

📅 Extra practical case: is it a leap year?

A year is a leap year if it's divisible by 4, but not by 100, unless it's also divisible by 400. Sounds tangled, right? In pseudocode it becomes clear:

START
  READ year
  IF (year MOD 4 = 0 AND year MOD 100 ≠ 0) OR year MOD 400 = 0 THEN
    WRITE year, " is a leap year"
  ELSE
    WRITE year, " is not a leap year"
  END IF
END

Chapter 4

The 3 building blocks that solve almost everything

Here's a secret: almost any program is built from just three pieces. Like Lego bricks: few shapes, millions of combinations. If you master them in pseudocode, you already know the most important part.

SequenceOne after anotherSteps happen in order. Changing the order changes the result.
DecisionChoose a pathIF this happens, do that; otherwise, do something else.
RepetitionGoing around in circlesRepeat a block as long as a condition holds.

Piece 1: sequence (order matters)

Imagine you have mango juice in glass A and pineapple juice in glass B, and you want to swap them without mixing. What do you need? A third glass. With variables it's the same:

START
  READ a
  READ b
  aux ← a      // keep a's value in the spare glass
  a ← b        // now a holds b's value
  b ← aux      // and b gets back what was a's
  WRITE a, b
END

Piece 2: decision (each question in its place)

Now let's classify a person by age: child, teenager or adult. Notice how one decision can live inside another:

  ELSE

    ELSE

Piece 3: repetition (going around with a head on your shoulders)

This is where the desk check really shines. We want to add the numbers from 1 to 4. You could do 1+2+3+4 = 10 in your head, but the plan has to work for 1 to 1000 too:

START
  counter ← 1
  sum ← 0
  WHILE counter ≤ 4 DO
    sum ← sum + counter
    counter ← counter + 1
  END WHILE
  WRITE sum
END

In a store, the cashier keeps scanning products and typing in each price. When she's done, she types 0. This value that signals "I'm finished" is called a sentinel.

  WHILE purchase ≠ 0 DO

Chapter 5

Your first pseudocode: the purchase discount

This is the problem that made everything click for me. A store wants to give a discount based on the purchase amount, and I tried to solve it straight in code, with a pile of nested conditions that tangled up like earphones in a pocket.

Here's how I solved it once I finally thought first. Follow these five steps, which work for any problem:

Step 1Understand it with an exampleSolve it by hand with a real case before writing anything.
Step 2Inputs and outputsWhat data do you get? What should come out?
Step 3Big stepsWrite the plan in 4 or 5 sentences, without details.
Step 4RefineTurn it into pseudocode with START, IF, END.
Step 5Test itDesk check with normal and borderline cases.

Steps 1 and 2: understand the problem

The store says: "if you buy less than $50, there's no discount; from $50 up to less than $100, 5%; from $100 up to less than $200, 10%; and $200 or more, 15%."

A hand example: if you buy $100, you get 10%, which is $10 off, so you pay $90. Now we know what to expect.

Input dataResults it must give
purchase amountpercentage, discount and total to pay

Steps 3 and 4: the plan in plain English, refined

The trick is to ask from highest to lowest. Look at the full plan:

START
  READ amount
  IF amount ≥ 200 THEN
    percentage ← 15
  ELSE
    IF amount ≥ 100 THEN
      percentage ← 10
    ELSE
      IF amount ≥ 50 THEN
        percentage ← 5
      ELSE
        percentage ← 0
      END IF
    END IF
  END IF
  discount ← amount * percentage / 100
  total ← amount - discount
  WRITE "Discount: ", discount
  WRITE "Total to pay: ", total
END

Chapter 6

The desk check in depth

You've already done several desk checks without realizing it. Now we're going to turn it into your superpower: a tool with a method, so that when something fails you know exactly where to look.

The 5 rules of a good check

Rule 1One column per variableIf a variable has no column, you'll lose track of it.
Rule 2One row per stepEvery line that runs is a row. Don't skip steps.
Rule 3Be a dumb computerRun what the plan says, not what you meant to say.
Rule 4Mark what changesColor or underline each new value. That way you can see the path.
Rule 5Choose your cases wellOne normal, one on the edge, and one weird (zero, empty, very large).

Step-by-step example: the largest of three numbers

A classic job interview question. The idea: we assume the first one is the largest and compare it with the others.

START
  READ a
  READ b
  READ c
  largest ← a
  IF b > largest THEN
    largest ← b
  END IF
  IF c > largest THEN
    largest ← c
  END IF
  WRITE "The largest is ", largest
END

🐛 Bug hunt 1: the sneaky division

Someone wrote this plan to average three grades. It looks perfect, but the desk check says otherwise:

START
  READ grade1
  READ grade2
  READ grade3
  average ← grade1 + grade2 + grade3 / 3
  WRITE average
END
grade1grade2grade3Real calculation (division goes first)average obtainedaverage expected
3333 + 3 + (3 / 3) = 3 + 3 + 173
5435 + 4 + (3 / 3) = 5 + 4 + 1104

Division is done before addition, just like in math. The fix: add parentheses.

  average ← (grade1 + grade2 + grade3) / 3

With the same values: (3 + 3 + 3) / 3 = 3 and (5 + 4 + 3) / 3 = 4. ✔

Chapter 7

Pseudocode with work cases

So far we've practiced with everyday examples. Now let's go to the office. Here are three cases I actually dealt with at work (with made-up data, of course): validating a form, building a report and designing an approval flow.

The nice thing is that in all three cases I did the same thing: first I drew or wrote the plan, then I tested it by hand, and only then did I touch a tool. And the tools were different: a web application, an SQL query and an automation platform. Same method, three destinations.

📝 Case 1: validating a registration form

The problem. A person signs up for a system and you need to check their data is correct before saving it. The rules are:

  • The name can't be empty.
  • The email must contain an at sign (@).
  • The age must be 18 or older.
  • The password must be 8 characters or longer.

A detail on how to read this plan. We use two "helpers" that exist in every language: contains(text, piece) answers yes or no, and length(text) counts the characters. They're called functions: they receive a value and return an answer.

The idea of the plan. Instead of stopping at the first error, we're going to count the errors with a variable called errors (an "accumulator"). That way, the person sees everything they need to fix in one go.

START
  READ name
  READ email
  READ age
  READ password
  errors ← 0
  IF name = "" THEN
    WRITE "Name is missing"
    errors ← errors + 1
  END IF
  IF NOT contains(email, "@") THEN
    WRITE "Invalid email"
    errors ← errors + 1
  END IF
  IF age < 18 THEN
    WRITE "You must be of legal age"
    errors ← errors + 1
  END IF
  IF length(password) < 8 THEN
    WRITE "The password must have 8 or more characters"
    errors ← errors + 1
  END IF
  IF errors = 0 THEN
    WRITE "Registration successful"
  ELSE
    WRITE "Fix ", errors, " field(s)"
  END IF
END

Chapter 9

Beginner mistakes (and how to dodge them)

Everyone makes them, me included. The good news is that there are always the same five. For each one I'll show you what it looks like, how the desk check exposes it and how to fix it.

Mistake 1: opening the editor before understanding the problem

What it looks like. Someone asks you to "calculate the tip" and you start typing. But... is the tip calculated before or after the ITBMS? Two reasonable people can understand different things. Look at both versions with a bill of $20:

// Version A: the tip is 10% of the subtotal
START
  READ subtotal
  itbms ← subtotal * 0.07
  tip ← subtotal * 0.10
  total ← subtotal + itbms + tip
  WRITE total
END
// Version B: the tip is 10% of the bill including ITBMS
START
  READ subtotal
  itbms ← subtotal * 0.07
  tip ← (subtotal + itbms) * 0.10
  total ← subtotal + itbms + tip
  WRITE total
END
Versionsubtotalitbmstiptotal
A201.402.0023.40
B201.402.1423.54

That's a 14-cent difference on a $20 bill. Across a thousand bills a day, it's an argument with the accountant. The solution isn't technical: it's asking.

💡 The 3 questions to ask before writing anything: (1) What data will I be given? (2) What exactly should come out? (3) Can you give me an example with real numbers? The third is the most powerful: if the other person can't give you an example, they don't have a clear idea of what they want either.

Mistake 2: copying code without understanding it

What it looks like. You find a snippet that "works", paste it and cross your fingers. When it fails, you don't even know where to start. The cure is the desk check. Let's look at a mysterious plan someone passed to you. What does it do?

START

  WHILE n > 0 DO
    r ← r * 10 + (n MOD 10)
    n ← n DIV 10
  END WHILE

END

Mistake 3: wanting to learn the whole language before mastering the logic

What it looks like. You buy three courses, memorize every Python function and still can't solve the problem "count how many even numbers there are". Look at the two routes:

🐢 Slow route

  1. Study the whole language.
  2. Watch 40 hours of videos.
  3. Try a real problem.
  4. Discover you don't know where to start.
  5. Frustration.

🚀 Fast route

  1. Solve a small problem in pseudocode.
  2. Test it by hand.
  3. Translate it to a language you already know.
  4. Learn only the new things you need.
  5. Repeat with a slightly bigger problem.

Logic is learned by solving problems, not by reading syntax. Here are ten problems to start with, from easiest to most challenging. Solve each one in pseudocode with its desk check before thinking about a language:

  1. Tell whether a number is even or odd.
  2. Find the largest of two numbers.
  3. Show the multiplication table of a number.
  4. Add up the even numbers from 1 to 20.
  5. Calculate the factorial of a number (5! = 120).
  6. Count how many digits a number has.
  7. Tell whether a number is prime.
  8. Convert seconds into hours, minutes and seconds.
  9. Calculate how much you pay for electricity based on consumption tiers.
  10. Game: guess a number using "higher" or "lower" hints.

Mistake 4: not testing with cases (not even by hand)

What it looks like. You test with a single "normal" value, it works, and you call it done. The cases that break programs are almost never the normal ones. One of the most dangerous is zero (or "no data"). Look at this plan for averaging grades:

START

    counter ← counter + 1

We've come to the question that brought you here: which language do I start with? The short answer is that, at this point, it hardly matters anymore. But since I know you want a concrete answer, I'll give you one using a method, not an opinion.

First, let go of the fear: choosing "wrong" hardly exists

The fear of getting it wrong comes from believing that what you learn in one language is lost if you switch. Look at what actually carries over:

The right question isn't "what's the best language?" but "what do I want to build?" Here's an honest guide that isn't the only truth but will help you get started:

📆 Practical case: the 30-day rule

The most expensive mistake after choosing is switching languages every week because "the other one looks easier". I suggest a commitment: 30 days with the same language before you consider switching. The plan is a rule with two conditions:

START
  READ days
  READ wantToSwitch    // "yes" or "no"
  IF days < 30 AND wantToSwitch = "yes" THEN
    WRITE "Not yet: finish your 30 days and ask again"
  ELSE
    IF days < 30 THEN
      WRITE "You're doing well: keep practicing"
    ELSE
      WRITE "You can calmly decide now whether to switch"
    END IF
  END IF
END
